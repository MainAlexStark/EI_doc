# EI_doc

Документооборот поверочных работ ООО «Единица Измерения».
Заменяет десктопное приложение EI_protocols (PyQt6 + Excel COM) и поглощает EI_HUB.

Документация: [архитектура](docs/architecture.md) · [нумерация протоколов](docs/numbering.md) ·
[условия поверки](docs/conditions.md) · [измерения](docs/measurements.md) ·
[журнал и нормоконтроль](docs/journal.md) · [аттестация ИО](docs/attestation.md) ·
[ассистент](docs/assistant.md) · [Аршин](docs/arshin.md) · [выезды](docs/logistics.md) ·
[синхронизация](docs/sync.md) · [договоры](docs/contracts.md) · [госзакупки](docs/tenders.md) ·
[персональные данные](docs/personal-data.md).

## Состояние

Этапы 0–5 дорожной карты закрыты в коде (см. [архитектуру](docs/architecture.md#дорожная-карта)).
Что есть:

- **Учёт поверок:** справочники (семейства, типы из Госреестра с подсказкой из ФИФ, эталоны,
  методики), поверки, протоколы, нумерация по времени поверки с подномерами для вставок
  задним числом, журнал погоды, калькулятор счётчиков воды с золотыми тестами.
- **Протоколы:** вёрстка Typst один в один с прежним `.xlsm`; при подписи выпускается PDF
  с графической подписью и клеймом поверителя, хранится с SHA-256 и не перезаписывается.
- **Журнал и нормоконтроль:** фильтры, выгрузка `.xlsx` формата ФИФ (49 колонок),
  предпросмотр пересчёта номеров, подпись пачкой, самопроверка хронологии.
- **Аршин:** очередь подписанных протоколов с причинами неготовности, пакеты XML для ЛК ФИФ,
  защита от повторной отправки, сверка с открытым реестром по расписанию.
- **Заявки (бывший EI_Hub):** публичная форма с капчей, подсказкой адреса и ценой, роутинг
  по районам, наряды, график доступности, Telegram-уведомления, договоры `.docx` по шаблону.
- **Поле:** PWA без связи — наряды и поверки в телефоне, очередь отправки по `client_id`,
  дельта-синхронизация по курсору, вход с привязкой к устройству и отзыв; бумажный бланк
  с QR и распознавание с обязательной сверкой.
- **Выезды:** спрос по районам на карте, командировки, маршрут по дням (OSRM или по прямой,
  OR-Tools при наличии), брони эталонов, PDF-пакет на выезд, план/факт.
- **Госзакупки:** сохранённые поиски ЕИС, уведомления о новых, воронка.
- **Задачи, ассистент-метролог, аттестация испытательного оборудования.**
- **Роли и права** (`apps/core/permissions.py`): владелец, руководитель, метролог,
  менеджер, поверитель, наблюдатель — одинаково в API, админке и интерфейсе.
- **152-ФЗ:** согласие с версией политики, `/privacy/`, сроки хранения с автоматическим
  обезличиванием, запрос субъекта, журнал действий с ПДн.
- **Эксплуатация:** docker compose за общим Caddy, `./deploy.sh` с откатом, ночные
  резервные копии с restic и ежеквартальной проверкой восстановления, CI на каждый push
  (ruff, тесты на SQLite и PostgreSQL, сборка фронта, shellcheck).
- Аудит изменений (`django-simple-history`), импорт исторического журнала
  (8073 из 8126 строк реального журнала).
- 450+ тестов; в CI — на SQLite и PostgreSQL, с typst (тесты PDF не пропускаются).

Что требует действий на сервере, а не кода — в конце этого файла, «Перед запуском».

## Запуск

```bash
cp .env.example .env
python -c "import secrets; print(secrets.token_urlsafe(64))"   # положить в SECRET_KEY
docker compose up -d --build
docker compose exec web python manage.py createsuperuser
```

Наружу ничего не выставлено (см. «Развёртывание на VPS» — публично торчит
только Caddy); для локальной проверки раскомментируйте `ports` у `web` в
`docker-compose.yml`. Тогда админка — `http://localhost:8000/admin/`,
схема API — `/api/docs/`.

## Развёртывание на VPS

Тем же способом, что и MCP-серверы (`ozon-seller-mcp`, `k8s-mcp`): общий Caddy
на машину, один Caddyfile на все сервисы, TLS от Let's Encrypt сам.

```bash
git clone https://github.com/MainAlexStark/EI_doc.git
cd EI_doc
./deploy.sh eidoc.example.com
docker compose exec web python manage.py createsuperuser
```

Скрипт заведёт `.env` из примера, сгенерирует `SECRET_KEY` и пароль БД,
пропишет домен в `ALLOWED_HOSTS`/`CSRF_TRUSTED_ORIGINS`, поднимет (или
переиспользует) общий Caddy в `/opt/infrastructure`, соберёт и запустит
сервер и дождётся ответа `/healthz` по HTTPS.

```bash
./deploy.sh update      # обновить до свежего коммита, с откатом при неудаче
./deploy.sh status      # что запущено и отвечает ли /healthz
./deploy.sh logs
./deploy.sh secrets     # где лежат пароли и адрес
```

Секреты живут в `.env` в корне репозитория (права 600) — тот же файл, что
читает локальная разработка без Docker, повторный запуск `./deploy.sh` их не
перевыпускает.

## Разработка без Docker

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r backend/requirements-dev.txt

cd backend
DJANGO_SETTINGS_MODULE=config.settings.local_sqlite python manage.py migrate
DJANGO_SETTINGS_MODULE=config.settings.local_sqlite python manage.py seed_catalog
DJANGO_SETTINGS_MODULE=config.settings.local_sqlite python manage.py seed_demo
DJANGO_SETTINGS_MODULE=config.settings.local_sqlite python manage.py runserver
```

Фронт отдельным процессом:

```bash
cd frontend && npm install && npm run dev    # http://localhost:5173
```

Вход демо-данных: `metrolog@ei.test` / `demo12345`. `seed_demo` работает
только при `DEBUG=True`.

Тесты (SQLite, быстро):

```bash
cd backend && pytest
```

Перед релизом (и в CI на каждый push) тесты гоняются на PostgreSQL — SQLite не
проверяет `select_for_update` и частичные уникальные индексы, а нумерация держится
именно на них:

```bash
cd backend && DJANGO_SETTINGS_MODULE=config.settings.test_postgres pytest -p no:cacheprovider
```

## Импорт старого журнала

Маппинг под «Журнал учёта поверочных работ Стариков» уже готов:

```bash
python manage.py import_journal \
    --file "Журнал учёта поверочных работ Стариков.xlsx" \
    --mapping apps/verification/mappings/journal_starikov.json --dry-run
```

На журнале от 03.09.2026: прочитано 8126 строк, перенеслось 8073, отклонено 53 —
все из-за пустой графы «Модификация СИ», то есть у записи нет наименования СИ.

Сопоставление идёт по **первой строке заголовка**, а не по индексу столбца:
заголовки в журнале — многострочные описания полей формата ФИФ, и перестановка
колонок ничего не ломает. Для другого журнала: `--inspect` напечатает заголовки
и заготовку маппинга.

## Реестр ФИФ

Схема открытого API Аршина публично не документирована и из среды разработки
недоступна. Перед первым использованием подсказки типов СИ выполните **на сервере**:

```bash
python manage.py fif_probe --query СВК
```

Команда покажет фактические имена полей в ответе и скажет, каких соответствий не
хватает, — после чего `FIELD_ALIASES` в `apps/arshin/fif.py` уточняется одной правкой.

## Что нельзя делать в этом репозитории

- Класть `.env` в git. Секреты живут на сервере.
- Ставить на сервер Excel, LibreOffice или headless-браузер ради генерации документов.
- Присваивать номер протокола руками в обход `apps.verification.numbering`.
- Править подписанный протокол. Правка — это новая версия со ссылкой на предыдущую.

## Перед запуском

Код готов; эти шаги делаются на сервере или организацией:

1. `.env`: `ARSHIN_SIGN_CIPHER` (шифр знака поверки), реквизиты `ORG_*` (договоры и
   политика ПДн), `RESTIC_*` (копии вне сервера), `LOGISTICS_DEPOT_*` (офис),
   `MAP_TILE_URL` (свой тайл-сервер или провайдер — OSM не разрешает рабочую нагрузку).
2. Проверки форматов, недоступных из среды разработки: `fif_probe` (реестр типов),
   XML пакета Аршин против действующей XSD из ЛК ФИФ (`docs/arshin.md`),
   `tenders_probe` (RSS ЕИС).
3. `deploy/osrm.sh volga-fed-district` — маршруты по дорогам (необязательно).
4. `./deploy.sh backup check` — убедиться, что копия восстанавливается.
5. 152-ФЗ вне кода: уведомление в Роскомнадзор, ответственный приказом, вычитка
   политики юристом (`docs/personal-data.md`).
6. EI_HUB: `.env` с `SECRET_KEY` и паролем БД был закоммичен в его репозиторий — ключи
   ротировать, историю вычистить (`git filter-repo`), это вне этого репозитория.
